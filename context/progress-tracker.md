## Database and Architecture

- Final feature 09 regression run: all 23 browser tests passed (10 existing UI/discovery and 13 auth tests), including signup, signin, OTP reset/resend, CAPTCHA refresh, redirect preservation, four-character animation and mobile overflow checks. Real PostgreSQL security suite: all 8 passed. Auth browser identity is isolated; live Supabase acceptance is still pending.

- Data access is server-only `pg` with parameterized SQL, a bounded pool and a dedicated limited `d2d_app` login. The application targets the dedicated `d2d` PostgreSQL database. Supabase Auth remains a separate identity provider.
- `DATABASE_URL` is migration-only; `APP_DATABASE_URL` is the limited runtime connection. Local secrets and CA certificates are ignored by Git. TLS verification uses the supplied database root CA certificate.
- Production catalogue reads require `DATABASE_CA_CERT_BASE64` in Vercel when the database CA is not in the system trust store. It overrides the local-only `DATABASE_CA_CERT_PATH`; without it, the deployed function can fail with `ENOENT` while opening the local certificate path. Redeployment and live verification remain pending.
- Existing public catalogue, customer request, favorites, saved-search and inquiry migrations are applied to `d2d`. Live limited-role/publication/customer RLS checks passed using rolled-back probe records.
- Initial empty catalogue tables remain in the default `postgres` database from setup before `d2d` was requested. The app connects to `d2d`.
- `db/demo-catalog.sql` provides optional, fictional public catalogue rows for disposable development or staging databases, using the base catalogue columns and existing local illustrative images. It is not applied by migrations and must not be run against production. The app still requires the later catalogue-field migration on the same database.
- Feature 09 migrations are applied in `d2d`; `AUTH_DATABASE_URL` uses the dedicated `d2d_auth` login. Real database tests verify that the public catalogue role cannot access CAPTCHA, OTP or auth rate-limit records and the auth role cannot read catalogue data.

## Blockers and Launch Gates

- Live Supabase Auth requires `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` and server-only `SUPABASE_SERVICE_ROLE_KEY`. Values have been requested for local configuration and must not be put in tracked files.
- Production OTP email provider and credentials are not approved. Development OTP output is explicitly user-authorized; production delivery will fail closed until an adapter/provider is approved.
- Auth rate-limit defaults are configurable and implemented with PostgreSQL atomic counters and HMAC identifiers; final thresholds must be measured and confirmed before launch. Configure a trusted proxy header explicitly outside Vercel; otherwise requests share a fallback bucket.
- Publishing/media permissions, provider/admin role workflows, booking transitions, pricing calculation, inquiries/favorite writes and distributed public catalogue abuse policies remain separate product/security decisions.
- No published catalogue or customer data is fabricated from reference-image sample prices, names, ratings, counts or verification badges.
- Eight moderate development-dependency advisories were previously reported. Reassess patched tooling before deployment; do not apply breaking audit fixes automatically.
